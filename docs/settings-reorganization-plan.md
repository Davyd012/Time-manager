# Settings reorganization plan

Status: proposed; no implementation included. Use `AGENTS.md` and `docs/ai/` as authority. Recheck the source before each implementation slice.

## Objective and current baseline

Organize settings around the person's task, reduce the long form, and preserve every existing action and data behavior. The supplied image is inspiration for its compact overview, leading icons, short summaries, dedicated project and allocation views, and clear empty states. It is not a palette specification.

Current source facts:

- Android `AppNavHost` opens `AppRoute.Settings` and renders `SharedSettingsScreen`; it injects Android-only `PlannorConnectionSection` into shared `TimnorSettingsSection`. The section currently mixes sign-in, project selection/linking, shared time, entry correction, allocations, review and confirmations in one scrollable column.
- `TimnorSettingsViewModel` owns backup, restore and document effects; Android's root document effect handler also serves Home spreadsheet export. Restore preview, confirmation, timer gate, failures and success must remain intact.
- The shared `TimnorApp` shell uses `SharedHomeRoute.Settings`, a saved Home route and a platform back callback. Its Settings screen has backup/restore; Android's Plannor integration is not automatically available on iOS. Do not imply cross-platform Plannor support or remove iOS document access.
- `TimnorTheme` currently supplies a warm neutral palette, including a dark `primary` that is almost black. Use actual theme roles and verify contrast in both modes; the image's luminous green, gradients, glow, decorative waves and primary-colored borders conflict with the design system and are not requirements.

## Information architecture

Use full screens for multi-step work, searchable or potentially long lists, and flows with state or keyboard input. Use a `ModalBottomSheet` for short contextual choices that return to a parent form; keep destructive confirmations in `AlertDialog` and native file pickers native. Do not nest sheets or use a sheet as the only way to reach a lengthy workflow.

| Destination | Overview entry and summary | Contents and behavior |
| --- | --- | --- |
| Settings | Top-level overview | Plannor account, Projects, Share and allocate time, Allocations and review, Backup and restore. Keep Home/Stopwatch navigation as currently provided by each host. |
| Plannor account | Connected username or disconnected status | Sign-in identifier/password, progress and failure, sign out. Clearly explain what connection shares using existing privacy copy. |
| Projects | Selected count, or connect prompt | Search, refresh, selection, archived status and per-project local linking/add/unlink. Long list has stable IDs. Selection retains current immediate `selectProject` semantics; do not add a misleading batch-submit CTA. |
| Share and allocate time | Short explanation | Separate create shared time from allocating an existing entry, with project/task, date, duration, private and shared notes as applicable. Show privacy distinction. Keep historical import and its preview reachable. |
| Allocations and review | Count only when trustworthy; otherwise neutral summary | Existing project allocations, refresh, select/correct/delete, pending/unknown/conflict/rejected/revoked results, retry and all existing review resolutions. Empty means confirmed empty, not loading or error. Do not claim records are shared *with* the user unless the underlying data supports that meaning. |
| Backup and restore | Brief data safety summary | Create backup, restore, storage note, progress and results. Preserve native document flows, preview counts/date, replacement confirmation and timer-block dialog. |

On Android, the Plannor overview entries and destinations reflect connection and existing capabilities. Disconnected entries lead to account connection or explain the prerequisite; they must not be silently absent if a user needs to discover them. Shared/iOS settings expose the supported backup destination; do not present nonfunctional Plannor entries. The image's “allocate existing hours” should map to the actual server-side `personalEntries` flow, not assume all locally registered hours are eligible. Preserve project linking and the separate new shared-time path, neither of which is fully represented by the image.

### Screen and sheet details

1. **Overview:** `TopAppBar` with back and localized title. A vertically scrolling list of full-width, single-action cards/rows in the order above. Each has an icon, title, at most two lines of supporting status, and trailing chevron. Account status and review-needed summary remain visible. Entire row opens its destination; no nested button within a clickable row. Use a single primary action only when a genuinely urgent next step exists, not a bright CTA on every card.
2. **Account:** For disconnected state show a compact explanation, identifier and password `OutlinedTextField`s, password masking and one full-width `Button` enabled only for valid input and idle state. Show loading and typed failure near the form. Connected state shows username and connection status, plus `OutlinedButton` or `TextButton` for sign out. Retain actual sign-out behavior; verify effect on pending writes before changing it. Handle IME and focus without exposing credentials in navigation arguments, saved UI state, logs or screenshots.
3. **Projects:** Top bar, explanation, localized selection count, search `OutlinedTextField`, refresh action, then `LazyColumn` of project rows. Each row has one accessible checkbox action, project name, context/organization and archived label. Checkbox state remains committed immediately as today; indicate loading/failure and keep previous state accurate. The link action opens a short sheet listing existing local projects, add-to-Timnor where allowed, unlink and cancel; use a searchable full screen instead if the local list can be long. Link action is a separate accessible target, not nested inside a clickable row. Preserve archived restrictions and current link eligibility.
4. **Share/allocate:** Use a screen with clearly labelled sections or tabs for create versus allocate. Render selected project, optional task, date, duration, notes, and submit according to the existing ViewModel contract. Project/task pickers may be sheets when short; long searchable lists become screens. Existing-entry selection shows date and remaining time; preserve correction and deletion with current eligibility and confirmation. Keep private and shared notes explicitly distinct. Never present an allocation as successful before the existing result reports it. Disable duplicate submission while loading; retain typed values on recoverable failure and show actionable status.
5. **Allocations/review:** Show progress, error/retry, confirmed empty, and populated states separately. Use readable cards with project, date and duration; provide explicit selection and correction/deletion actions. Surface pending/unknown outcomes and retry, and all review choices with local/remote information and existing eligibility conditions. Keep import preview and destructive confirmations as dialogs. Do not compress conflicting details into an icon alone.
6. **Backup:** Explain file contents and replacement behavior before actions. Use one filled create action and an outlined restore action; stack when width or text scale requires it. Preserve progress, native cancellation as no-op, result messages, preview metadata and existing timer block/route to Stopwatch. Show the result after returning from the native picker even if the user navigated away; maintain one effect collector at the host root.

## Detailed visual specification

The image suggests a dense, structured dashboard with a strong top bar, icon tiles, outlined rows and a fixed lower action on focused tasks. Translate its hierarchy into the existing Material 3 system:

- **Canvas and structure:** Use `Scaffold`/`Surface` with `MaterialTheme.colorScheme.background` for the large screen area and `surface` for cards and sheets. Use the existing shell's insets and bottom navigation once, avoiding duplicate safe-area padding. The title bar uses `TopAppBar`, `titleLarge`, `onSurface` and an `IconButton` back control. Subscreen back label describes its actual destination, not always Home. Use existing width constraints where available; on wide layouts constrain readable content rather than stretching rows indefinitely.
- **Spacing:** Use `MaterialTheme.timnorSpacing`: `medium` (16 dp) screen inset and standard card content; `small` (8 dp) between icon/text and nearby rows; `large` (24 dp) between major sections; `extraLarge` (32 dp) for spacious empty-state separation. Use the existing `extraSmall` only for tightly related labels. Allow vertical scroll, text wrapping and taller rows instead of fixed heights. Maintain at least 48 dp interactive targets.
- **Cards and rows:** Prefer Material 3 `Card` or `Surface` with `surface`, `MaterialTheme.shapes.medium` and an `outlineVariant` border only if needed to distinguish adjacent surfaces. No primary border, custom shadow or translucent gray. Icon tile uses `primaryContainer` with `onPrimaryContainer`, `MaterialTheme.shapes.small` or `medium`; use a standard Material icon or existing shared drawable with consistent visual size. Use a trailing chevron in `onSurfaceVariant`. Decorative icons have null descriptions when adjacent text already names the action.
- **Typography:** Screen title `titleLarge`; card/row title `titleMedium`; group headings `titleMedium` or `titleSmall`; supporting descriptions `bodyMedium`; metadata/status `bodySmall` in `onSurfaceVariant`. Primary text uses `onSurface`. Use a text status alongside icons and selected controls; never signal state through color alone. Do not create inline `TextStyle`, sizes, weights or manual line heights.
- **Controls:** Primary screen action uses Material 3 `Button` and the theme's `primary`/`onPrimary` defaults only after checking actual contrast; secondary actions use `OutlinedButton`, `TextButton`, or standard icon buttons. The existing dark primary may need a separately reviewed **theme-level** correction if it is not distinguishable; do not introduce a settings-only green palette. `OutlinedTextField` supplies search, account and note fields. `Checkbox` uses standard selected/disabled semantics. Selected rows can use `primaryContainer` with `onPrimaryContainer` when necessary, while outlines remain `outlineVariant`; ensure the visual and text contrast is tested in both schemes.
- **Status:** Normal connection and selection summaries use text and, where useful, a Material chip with `primaryContainer`/`onPrimaryContainer`. Errors use `error`/`onSurface` as appropriate, with explanation and retry; destructive confirmation uses error roles only for destructive emphasis. No improvised amber warning token. Progress uses `CircularProgressIndicator` with a localized label. Persistent failures remain visible; use a snackbar only for transient feedback.
- **Empty state:** Center a standard meaningful icon and `titleMedium` plus short `bodyMedium` explanation in the available content region, with a relevant action only if one exists. Use `onSurfaceVariant` for supporting text; no glowing illustration or wave. State must remain reachable to screen readers and not hide errors or filters.
- **Sheets and dialogs:** `ModalBottomSheet` uses Material defaults, `surface`, `MaterialTheme.shapes`, a descriptive title, safe insets and a scrollable choice list. Dismiss via back, scrim or explicit cancel without changing selection until the chosen action is invoked. Do not replace the restore or deletion `AlertDialog` with a casual sheet. Keep confirm/cancel labels explicit.
- **Motion and adaptability:** Prefer default Material transitions and simple state animations only when useful; respect platform reduced-motion behavior. No infinite glow or decorative animation. Test large font scaling, long translations, keyboard/IME, narrow and wide windows, light/dark, system insets and landscape. Sticky submit actions must leave the scrollable content visible above the IME and shell navigation.

## State, navigation and implementation

1. Inventory actual Android and iOS hosts, all ViewModel intents, native result handlers, string resources and current back/tab behavior before editing. Record each existing operation against its destination, including review branches and historical import. Capture baseline screenshots and interaction behavior.
2. Add typed Android `AppRoute` destinations and wire them through `NavHost`/`Navigator`, using callbacks from stateless presentation. Route arguments carry stable identifiers only, never credentials or mutable objects. Scope the existing `PlannorConnectionViewModel` above the related routes so navigation does not reset operations or duplicate subscriptions; verify the current factory/owner before choosing the scope. Keep its current StateFlow and data contracts initially; split state only where clearly necessary without changing repository behavior.
3. Make the shared settings overview and backup screen reusable with explicit typed state and callbacks. Replace the broad `additionalContent` slot with a small capability/entry interface or host-provided overview entries; Android supplies Plannor navigation and iOS supplies only supported entries. Do not move Android repositories, `Context`, or Android `R` into `commonMain`. Use shared Compose resources for shared labels and Android resources for Android-only labels, updating all existing locales according to the localization guide.
4. For shared `TimnorApp`, extend its existing typed navigation state and saveable back handling for backup, preserving the selected Home route across tab switches. Android's Navigation3 host and the shared shell are distinct: wire and test both rather than assuming `AppRoute` is shared. Back dismisses dialogs/sheets first, then returns one screen at a time to Settings, then Home; Home reselection retains established shell behavior. Specify and test what happens on tab changes and process recreation, preserving safe form state where supported without saving passwords or replaying writes.
5. Extract focused stateless components under their feature's `presentation` folder: overview row, status, account form, project row/link sheet, time form, allocation/review card, backup content and dialogs. Keep route/host responsible for collecting state once and connecting callbacks. Keep composables small and business rules in the ViewModel/domain. Use stable lazy-list keys; do not duplicate data or networking in UI.
6. Preserve the root document-effect collector, platform picker callbacks and restore success refresh. Preserve restore's preview, confirmation, timer gate and data replacement behavior; do not change backup format or storage as part of layout work. Audit asynchronous effects on navigation, cancellation, sign-out, retry and recreation so operations are neither lost nor repeated. Show result in a relevant reachable destination.
7. Migrate one destination at a time behind existing navigation, verify its actions, then remove obsolete embedded UI only when both paths and hosts remain functional. Avoid treating older `docs/SHARED-UI-PARITY-PLAN.md` implementation descriptions as current without checking code.
