Source audit of the current working tree, 2026-11-10. Android's `AppNavHost` now renders the shared Home, Stopwatch, Month View and Settings screens. The older Android feature composables are a reference, not the UI currently displayed by that host. `TimnorApp` is the separate shared shell used by the iOS host. These files record observable source behavior, known differences, implementation updates and verification. “Present” means code exists, not that its appearance or gesture has passed device testing. This pass compiled shared Android and Android instrumentation code and ran unit/host tests, but did not obtain matching legacy/shared screenshots or connected interaction results: the tablet disconnected and no emulator is installed. iOS Kotlin targets cross-compiled; no Xcode app, simulator, or accessibility inspection was available. The older `docs/SHARED-UI-PARITY-PLAN.md` describes an earlier starting point and should not be used as a current inventory.

## How to use these notes

1. Read repository `AGENTS.md`, `CAVEMAN.md` and the relevant `/docs/ai/` guides first. Paths in the screen notes are relative to the repository root unless a shared feature path is explicitly introduced. Inspect the current working tree before editing; the inventory is a snapshot and files may have changed.
2. Pick one screen and trace its active host → screen → leaf composable → callback → ViewModel → persistence/platform effect. Do not assume the legacy Android composable is still active: `AppNavHost` invokes the shared screens.
3. Treat **current** as a source observation, **gap** as a source-supported difference, and **verify** as a question, not permission to invent a behavior. Where the legacy expectation is uncertain, inspect its call sites and tests, then compare a reference build. Preserve existing behavior until evidence justifies a change.
4. Port one interaction at a time. Keep presentation state and durable domain state separate, use existing theme/resources, and use narrow platform adapters for native work. Avoid replacing the ViewModel, data schema or the user's existing uncommitted changes.
5. Add behavior-focused tests where required by the testing guide. Report code paths checked, commands and device/OS results, plus unresolved questions. Do not mark visual parity complete without matching reference captures.

## Acceptance for every screen

1. Capture the legacy reference and shared screen with the same data, device size, locale, font scale and light/dark theme. The active Android host uses shared UI, so a separate reference build or reviewed historical screenshots are needed; do not label a screenshot of the active host as legacy.
2. Compare empty, populated, loading, error, disabled, keyboard, sheet and dialog states. Exercise tap, long press where applicable, directional drags, interrupted gestures, cancellation, navigation and process recreation.
3. Test TalkBack/VoiceOver labels, focus order, 48dp targets, large text, narrow screens, system insets and reduced motion. Check horizontal gesture direction in RTL.
4. Run the relevant shared unit tests and Android Compose interaction tests. Run connected tests and review screenshots on an Android device; build and exercise iOS on a Mac. Record device, OS, build, results and intentional differences. Compilation alone is not visual or gesture parity.
5. Use the existing Material 3 theme, spacing and localization resources. Keep state and persistence behavior intact; do not replace data or silently alter destructive flows to match a screenshot.
